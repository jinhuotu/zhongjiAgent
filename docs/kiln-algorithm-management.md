# 新增算法的管理流程

管理员可直接使用「上传算法包」接入可训练 Python ZIP，详见 [Python 算法包接入](kiln-algorithm-packages.md)。下文的受控清单和绑定接口适用于随代码部署的实现，训练验证及发布规则同样适用于上传包。

## 本次交付范围

新增独立页面 `/algorithm-manage`（决策分析 → 算法管理），业务算法库也提供管理员入口及刷新按钮。
这是一套受控新实现的登记、真实训练验证和发布流程，没有新增虚构算法。登记名称不会生成代码。
管理员先登记需求，研发按接入指南部署独立 `fit/predict` 实现，再绑定、验证、发布。
不能把已有内置算法重新命名当作新算法；已有参数方案、外部冻结模型仍保持原入口与语义。

当前按账号发布，供同一账号的建模项目使用；没有实现跨账号共享或组织级发布。
管理端所有接口均用后端 `AdminUser` 鉴权；前端菜单同时限制管理员，前端隐藏不是权限边界。

## 状态与数据

待绑定 `draft` → 待验证 `bound` → 验证中 `validating` → 验证通过 `validated` → 已发布 `published` → 已停用 `retired`。
验证异常进入 `failed`，可从管理页面重新校验并启动任务；服务中断的任务也从管理页重新验证。
重新绑定会清除当前验证依据。验证中、已发布、停用的记录禁止覆盖绑定；修改实现须新增独立版本键和记录。

复用 `kiln_studio_assets`，不修改表结构：

- `algorithm_release` 保存需求、绑定实现/版本/指纹、状态、最近验证和任务 ID、带时间的操作记录。
- `algorithm_check` 保存真实验证指标、输入版本、数据哈希、机理版本、保存恢复差异、输出时距及产物引用。
- 既有 `job` 增加 `algorithm_validate` operation，用真实阶段状态展示进度，没有定时假进度。

新实现即使已经注册且状态 enabled，未发布也不会出现在账号的业务算法库，直接提交实验键也会被拒绝。
停用只阻止新实验选择；历史权重、报告与回调不删除，已排队且固定实现的实验可以继续，历史推理保持可恢复。
原七种内置算法不追溯要求发布记录，旧六步流程及旧导出保持现有契约。

## 验证与发布条件

1. 校验当前账号对项目、数据、机理的访问权及版本关联；Pydantic 参数必须合法，验证只选绑定算法。
2. 按现有因果窗口拆分训练/验证/测试，只把训练窗口交给 fit，生成真正可序列化的权重。
3. 核对留出输出有效、JSON 保存恢复一致、单点和批量一致；有路径回调时核对声明的全部 offsets 和端点一致性。
4. 保存真实验证/测试误差、覆盖率、核对输入数量、耗时、划分口径及限制说明，不生成展示数字。
5. 发布只接受当前绑定版本最近一次成功报告；核对实现与运行指纹，发布者还需填写适用范围和效果确认说明。

技术验证通过不等于准确率达标。验证报告只说明所选任务/窗口/数据的结果，不保证所有任务或工况。
训练回调没有接收验证/测试标签，但其内部是否读取其他文件或未来数据仍需研发审查；不能声称自动证明没有泄漏。
当前验证未自动执行 ONNX/Python 交付核对，更不代表量化、TensorRT 或目标硬件性能通过。

绑定指纹包含回调代码及所在模块、声明、参数契约和 Python/NumPy 版本，用来发现常见部署不一致。
它不是任意第三方依赖的完整供应链签名，也不是算法包安全认证。第三方依赖和外部文件变化需要研发管理版本。
新算法进入正式实验时也固定指纹；排队后代码/契约变化会明确失败，不能静默用新实现跑旧任务快照。

## 接口

统一前缀 `/api/v1/kiln-studio`，以下管理接口均要求管理员，记录与任务同时按当前账号取数：

- `GET /algorithm-management`：真实登记记录、运行问题和已部署实现清单。
- `POST /algorithm-management`：登记新算法需求（name、description、requestedKey）。
- `POST /algorithm-management/{id}/bind`：绑定真实 implementationKey/version，禁止已有内置键。
- `POST /algorithm-management/{id}/validate`：projectId 和完整 ExperimentRequest，创建真实验证任务。
- `GET /algorithm-management/{id}/job`：最近验证任务状态及真实错误。
- `GET /algorithm-management/{id}/validation`：当前有效验证报告。
- `POST /algorithm-management/{id}/publish`：validationId 和非空发布说明。
- `POST /algorithm-management/{id}/retire`：非空停用原因。

非法请求 422；状态/版本冲突 409；越权记录按 404 处理，普通用户访问管理端 403。
管理验证任务不能从原通用重试入口绕过绑定与权限检查，须重新从管理页启动。

## 运行边界

随代码部署的受控实现复用 BackgroundTasks / asyncio.to_thread。上传包使用独立容器执行，由平台传递固定的 12 个特征与 JSON 权重。16×7 序列接口仍适用于随代码部署的受控实现。

## 验证文件与运行

`tests/test_kiln_algorithm_management.py` 使用隔离注册表中的测试算法与 SQLite 验证完整生命周期、失败拦截、
账号隔离、接口权限、版本漂移和正式实验指纹。测试实现不会出现在生产算法清单。
前端 `tests/kiln-algorithm-management.test.mjs` 验证各状态按钮和漂移禁用。
执行命令沿用接入指南的现有 venv pytest、Node 原生测试及 `npm run build`。

代码更新后需部署并重启 API/实验执行进程，更新前端后重新获取菜单；当前工作中的生产服务未被本次操作重启。
